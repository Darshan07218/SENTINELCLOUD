# Phase 9 — Kubernetes Deployment

> **Note (Phases 12–13).** Commands and behaviour in this phase document
> predate the security hardening and the engineering review. Notably: sign-up
> always creates a `CITIZEN` (no `role` field), the refresh token is an
> httpOnly cookie (login returns `accessToken`, not `session.accessToken`),
> every service except `/auth/docs` requires a Bearer token, and secrets come
> from `./scripts/generate-secrets.sh`. Current commands:
> [`SYSTEM-REFERENCE.md`](SYSTEM-REFERENCE.md), [`../SECURITY.md`](../SECURITY.md).


## Goal

Run the whole SentinelCloud system on a local Kubernetes cluster
(Kind or Minikube, both free) with production-style manifests:
Deployments, Services, ConfigMaps, Secrets, PersistentVolumes,
HorizontalPodAutoscalers, startup/readiness/liveness probes, resource
requests and limits, and internal service discovery. Then demonstrate
scaling.

No paid cloud service is used anywhere. Everything below runs on a
laptop.

## 1. Architecture on Kubernetes

```
                         your browser
                              │  http://localhost:30080  (Kind)  ·  port-forward / minikube service
                              ▼
 ┌───────────────────────── namespace: sentinelcloud ─────────────────────────────┐
 │                                                                                 │
 │  Service frontend (NodePort 30080 → 8080)                                       │
 │     └─ Deployment frontend ── nginx: serves React bundle,                      │
 │                               proxies /api, /ws, /health  ──┐                   │
 │                                                              ▼                  │
 │  Service gateway (ClusterIP :8080)                                              │
 │     └─ Deployment gateway ── JWT check + RBAC, proxies by Service name:         │
 │          auth-service:8081   hospital-service:8082   ambulance-service:8083     │
 │          blood-bank-service:8084   power-service:8085   disaster-service:8086   │
 │          notification-service:8087 (REST + /ws/live WebSocket)                 │
 │                                                                                 │
 │  each = ConfigMap + Deployment + ClusterIP Service + HorizontalPodAutoscaler    │
 │                                                                                 │
 │  StatefulSet postgres  ── PVC data-postgres-0 (2Gi)   6 databases, 1 instance   │
 │  StatefulSet rabbitmq  ── PVC data-rabbitmq-0 (1Gi)   topic exchange + queues   │
 │  StatefulSet redis     ── PVC data-redis-0 (512Mi)    recent-events history     │
 └─────────────────────────────────────────────────────────────────────────────────┘
```

Only **one** Service is reachable from outside the cluster: `frontend`.
nginx inside the frontend pod reverse-proxies `/api/*`, `/ws/*` and
`/health*` to the gateway, so the browser talks to a single origin. That
means no CORS and no gateway hostname baked into the JS bundle. The
gateway and every domain service are `ClusterIP`, so they're only
reachable from inside the cluster.

a Kustomize **base** (`k8s/base/`, environment-independent) plus a

would reuse the same base unchanged. One command
(`kubectl apply -k k8s/overlays/local`) deploys the whole system.
Kustomize is built into `kubectl`; there's nothing extra to install.

## 2. Code changes Kubernetes required (and why)

Most of the application runs unchanged. Service names in Kubernetes
are the same as Compose container names, so `http://hospital-service:8082`
resolves either way. The exceptions below are bugs that never showed up
under Compose because Compose only ever ran one container per service.
Each one would break the system as soon as `--replicas=3` (or the HPA)
ran.

### 2.1 Migration race between replicas (Node services)

**Bug:** `runMigrations()` reads `schema_migrations` and then applies
missing files. If three hospital-service pods start at the same moment,
all three see `0001_create_hospitals.sql` as pending and all three run
`CREATE TABLE`. One wins; the other two crash. The "seed only if the
table is empty" check has the same race and can insert the demo data
twice.

**Reproduced on a real PostgreSQL 16 server** with three concurrent
sessions running the runner's exact check-then-apply logic:

```
WITHOUT lock (Phase 8 runner, 3 pods start together):
  replica-3 exit=0 NOTICE:  applied migration
  replica-2 exit=1 ERROR:  duplicate key value violates unique constraint "pg_type_typname_nsp_index"
  replica-1 exit=1 ERROR:  relation "schema_migrations" already exists
WITH pg_advisory_lock (Phase 9 withStartupLock):
  replica-1 exit=0 NOTICE:  applied migration
  replica-3 exit=0 NOTICE:  relation "schema_migrations" already exists, skipping
  replica-2 exit=0 NOTICE:  relation "schema_migrations" already exists, skipping
rows in schema_migrations: 1
```

**Fix:** a new `withStartupLock()` helper in `src/db.js` of auth, hospital,
ambulance and disaster wraps migrations and seeding in
`pg_advisory_lock`, a Postgres-wide mutex. The first pod does the
work; the others wait, then find nothing to do. If a pod dies while
holding the lock, Postgres ends its session and releases the lock, so
there is never a stale lock to clean up.

**Java services:** Flyway already locks its own history table, so
schema migrations were safe there. The `DemoDataSeeder`s had the same
"count() == 0 → insert" race. Their `run()` is now `@Transactional` and
first takes `pg_advisory_xact_lock`, which is released automatically at
commit.

### 2.2 Live feed lost events with more than one notification-service replica

**Bug:** every notification-service replica consumed the same durable
queue `q.notifications.all-events`. RabbitMQ round-robins a shared queue
between consumers. With 3 replicas, a browser whose WebSocket landed on
replica A would only see the ~⅓ of events RabbitMQ delivered to A.

**Fix (`notification-service/src/index.js`):** two consumers per pod.

| Queue | Type | Purpose |
|---|---|---|
| `q.notifications.all-events` | shared, durable | writes each event to the Redis history **exactly once** (competing consumers is the right behaviour here) |
| `q.notifications.live.<pod-name>` | exclusive, auto-delete, one per pod | every pod gets **every** event and pushes it to its own WebSocket clients |

Because the per-pod queue is `exclusive` + `autoDelete`, RabbitMQ deletes
it automatically when its pod goes away, so scaling down leaves no
orphaned queues behind.

### 2.3 RabbitMQ: give-up-after-30s and no reconnect

**Bug:** every Node service tried RabbitMQ 10 × 3s at startup, then gave
up **for the rest of the process's life**, and nothing reconnected after
a broker restart. On a fresh cluster RabbitMQ (image pull + Erlang boot)
often takes longer than 30s. The result: hospital/ambulance running
forever without their disaster consumers, and disaster-service (whose
readiness requires the broker) never becoming Ready.

**Fix:** `connectBrokerWithRetry()` now retries forever with capped
backoff. `connectBroker()` takes an `onClose` hook, so a lost connection
triggers a reconnect **and** re-registers the consumers on the fresh
channel. The Spring services already get this from Spring AMQP's
built-in connection recovery.

### 2.4 Graceful shutdown (SIGTERM)

**Bug:** Node running as PID 1 in a container has **no default SIGTERM
handler**. Every scale-down or rolling update therefore waited the full
30s grace period and then SIGKILLed the pod mid-request.

**Fix:** every Node service closes its HTTP server on SIGTERM, lets
in-flight requests finish, closes its DB pool and exits. The Deployments
add a `preStop: sleep 5` so the pod is removed from the Service's
endpoints **before** SIGTERM arrives. Spring Boot gets
`server.shutdown: graceful` with a 20s drain. Measured on the test
cluster: `kubectl delete pod` → SIGTERM 5.3s later (the preStop window)
→ pod gone at 6.0s, instead of 30s.

### 2.5 Smaller fixes

| Change | Why |
|---|---|
| Dockerfiles: `USER 1000:1000` (Node), `USER 1001:1001` (Java), nginx-unprivileged uid 101 | `runAsNonRoot: true` can only be verified against a **numeric** user |
| Java: `JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=65 -XX:+ExitOnOutOfMemoryError` | the default heap is 25% of the container limit, too small for Spring Boot in 768Mi |
| Spring readiness group = `readinessState, db` | `/health/readiness` now actually reflects DB reachability |
| `frontend/Dockerfile` → production nginx image (old one kept as `Dockerfile.dev`) | the Vite dev server is not a production server; nginx also gives same-origin `/api` + `/ws` |
| `getLiveFeedUrl()` resolves against `window.location` | the API base is now the relative `/api/v1` |
| gateway `xfwd: true` + auth-service `trust proxy` (private ranges only) | the login rate limiter was keying on the **gateway's** IP, so every user shared one 20-per-15-minutes bucket |
| `docker-compose.yml`: added `JWT_ACCESS_SECRET` to disaster-service | **pre-existing bug:** its auth middleware refuses to start without it, and Compose never passed it |
| `.dockerignore` in every service | keeps local `node_modules`, `.env` and `target/` out of images |

## 3. Prerequisites

| Tool | Version | Notes |
|---|---|---|
| Docker Desktop / Docker Engine | 24+ | Kind runs its nodes as Docker containers; both tools build images with Docker |
| kubectl | 1.27+ | includes Kustomize (`-k`) |
| **Either** Kind | 0.20+ | https://kind.sigs.k8s.io/docs/user/quick-start/#installation |
| **or** Minikube | 1.32+ | https://minikube.sigs.k8s.io/docs/start/ |

**Resources:** the full stack *requests* ~1.5 CPU and ~2.5 GiB of memory
at one replica each (see §9), plus Kubernetes' own system pods. Give
Docker Desktop (or Minikube) **at least 4 CPUs and 6 GiB of RAM**. With
2 CPUs, some pods will sit in `Pending` with `Insufficient cpu`.

All commands below are run from the **repository root**.

## 4. Option A — Kind (recommended)

### 4.1 Create the cluster

```bash
kind create cluster --config k8s/cluster/kind-cluster.yaml
kubectl cluster-info --context kind-sentinelcloud
kubectl get nodes
```

This gives you 3 nodes (`sentinelcloud-control-plane`, `sentinelcloud-worker`,
`sentinelcloud-worker2`). Node port 30080 is mapped to `localhost:30080`.

### 4.2 Install metrics-server (required for the HPAs)

Kind doesn't ship one. Install it, then allow it to talk to Kind's
self-signed kubelets:

```bash
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
kubectl patch deployment metrics-server -n kube-system --type=json --patch-file k8s/cluster/metrics-server-kind-patch.json
kubectl rollout status deployment/metrics-server -n kube-system
```

### 4.3 Build the images and load them into Kind

Kind nodes can't see your local Docker images until you load them in.

```bash
docker build -t sentinelcloud/gateway:1.0.0              services/gateway
docker build -t sentinelcloud/auth-service:1.0.0         services/auth-service
docker build -t sentinelcloud/hospital-service:1.0.0     services/hospital-service
docker build -t sentinelcloud/ambulance-service:1.0.0    services/ambulance-service
docker build -t sentinelcloud/blood-bank-service:1.0.0   services/blood-bank-service
docker build -t sentinelcloud/power-service:1.0.0        services/power-service
docker build -t sentinelcloud/disaster-service:1.0.0     services/disaster-service
docker build -t sentinelcloud/notification-service:1.0.0 services/notification-service
docker build -t sentinelcloud/frontend:1.0.0             frontend

kind load docker-image --name sentinelcloud sentinelcloud/gateway:1.0.0 sentinelcloud/auth-service:1.0.0 sentinelcloud/hospital-service:1.0.0 sentinelcloud/ambulance-service:1.0.0 sentinelcloud/blood-bank-service:1.0.0 sentinelcloud/power-service:1.0.0 sentinelcloud/disaster-service:1.0.0 sentinelcloud/notification-service:1.0.0 sentinelcloud/frontend:1.0.0
```

Shortcut (bash / Git Bash / WSL): `./scripts/k8s-build-images.sh kind`

The first build takes several minutes, because Maven downloads Spring
Boot's dependencies for the two Java services.

### 4.4 Deploy

Create the local Secret file first (once). It's gitignored, like the
root `.env`. Phase 12: it is generated with random values (Windows: run
it in Git Bash or WSL) — the services refuse example passwords:

```bash
./scripts/generate-secrets.sh k8s
```

```bash
kubectl apply -k k8s/overlays/local
kubectl get pods -n sentinelcloud -w        # Ctrl+C once everything is 1/1 Running
```

Or block until everything is Ready (the first start can take 3–5
minutes: Postgres, Redis and RabbitMQ images pull from Docker Hub, and
the Spring services take a while to boot):

```bash
kubectl wait --for=condition=Ready pods --all -n sentinelcloud --timeout=600s
```

### 4.5 Open it

http://localhost:30080. Log in with `admin@sentinelcloud.local` and the
`DEFAULT_ADMIN_PASSWORD` from `k8s/overlays/local/secrets.env` (randomly
generated — Phase 12).

## 7. Scaling demo — `kubectl scale deployment --replicas=3`

### 7.1 Run it

```bash
kubectl get deployment hospital-service -n sentinelcloud          # READY 1/1
kubectl scale deployment hospital-service --replicas=3 -n sentinelcloud
kubectl get pods -n sentinelcloud -l app.kubernetes.io/name=hospital-service -w
```

What the watch shows (recorded on the test cluster, abbreviated):

```
t+2s   hospital-service-…-45kdj 0/1 Init:0/1   hospital-service-…-4jktt 0/1 Init:0/1   hospital-service-…-pl2hm 1/1 Running
t+4s   hospital-service-…-45kdj 0/1 Running    hospital-service-…-4jktt 0/1 Running    hospital-service-…-pl2hm 1/1 Running
t+6s   hospital-service-…-45kdj 1/1 Running    hospital-service-…-4jktt 1/1 Running    hospital-service-…-pl2hm 1/1 Running
```

With the real image, the `0/1 Running` phase lasts a few seconds longer
(DB connection + migration check).

```bash
kubectl rollout status deployment/hospital-service -n sentinelcloud
kubectl get endpointslices -n sentinelcloud -l kubernetes.io/service-name=hospital-service
kubectl get pods -n sentinelcloud -l app.kubernetes.io/name=hospital-service -o wide   # spread across Kind's 2 workers
```

### 7.2 What happens, step by step

1. **API server.** `kubectl scale` changes one field, the Deployment's
   `spec.replicas`, from 1 to 3, and stores it in etcd. Nothing else
   happens synchronously.
2. **Deployment controller.** It sees desired 3 ≠ current 1 and raises
   the replica count on the Deployment's current **ReplicaSet**.
3. **ReplicaSet controller.** It creates two new **Pod objects** from the
   pod template. They start in `Pending`, with no node yet.
4. **Scheduler.** It picks a node for each pod. A node only qualifies if
   it has the pod's resource **requests** free (100m CPU, 128Mi memory),
   so requests are what make scheduling safe. The `topologySpreadConstraints`
   prefer putting replicas on different nodes, which you can see on
   Kind's two workers with `-o wide`.
5. **Kubelet on that node.** It uses the local image (`imagePullPolicy:
   IfNotPresent`, so no registry needed), runs the **init container**
   `wait-for-postgres` (`nc -z postgres 5432`), then starts the app
   container → `Init:0/1`, then `0/1 Running`.
6. **Application start-up.** The new pod connects to Postgres and takes
   the startup lock (§2.1). Migrations are already applied ("no pending
   migrations") and seeding is skipped because the tables aren't empty,
   so the new replicas never touch existing data. Then the HTTP server
   starts.
7. **Probes.** The **startup probe** (`/health`) passes as soon as the
   server listens. Then the **readiness probe** (`/health/ready`, which
   runs `SELECT 1` against Postgres) passes → the pod becomes `1/1 Ready`.
   **Until that moment it receives no traffic.**
8. **Endpoints.** The EndpointSlice controller adds each newly Ready
   pod's IP to the `hospital-service` Service. kube-proxy on every node
   rewrites its iptables/IPVS rules, so the Service's ClusterIP now
   balances new connections across all 3 pods.
9. **Nobody else changes anything.** The gateway still calls
   `http://hospital-service:8082`. That DNS name still resolves to the
   same ClusterIP, and only the set of pods behind it changed. This is
   what Kubernetes service discovery buys you.
10. **RabbitMQ.** Each new pod connects to RabbitMQ and starts consuming
    `q.hospital.disaster-events`. The queue is shared, so the three
    replicas are **competing consumers**: a `disaster.detected` event is
    processed by exactly **one** replica. That's what you want here (one
    capacity report per disaster, not three).

### 7.3 See the load balancing

```bash
kubectl exec -n sentinelcloud deploy/gateway -- sh -c 'for i in $(seq 12); do wget -qO- "http://hospital-service:8082/health?demo=$i" >/dev/null; done'
kubectl logs -n sentinelcloud -l app.kubernetes.io/name=hospital-service --prefix --since=1m | grep demo
```

`--prefix` shows which pod served each request. On the test cluster, 12
fresh connections split 7 / 4 / 1 across the three pods. kube-proxy's
default iptables mode picks a backend **at random per new
connection**, not strict round-robin.

> **Note:** balancing is per **connection**, not per request. The
> gateway's proxy reuses keep-alive connections, so with light traffic
> one replica can serve most gateway → hospital requests. Under real
> concurrent load the proxy opens more connections and the spread
> evens out. Per-request balancing would need an L7 proxy or service mesh.

### 7.4 The HPA will take the replica count back

Every Deployment here also has a **HorizontalPodAutoscaler**, and the HPA
owns `spec.replicas`. That's also why the Deployment YAML deliberately
doesn't set `replicas`. After a manual scale to 3 with no load, the HPA
computes that 1 replica is enough, so:

```bash
kubectl get hpa hospital-service -n sentinelcloud -w
kubectl describe hpa hospital-service -n sentinelcloud      # see Events
```

Observed on the test cluster, from the HPA's events:

```
Normal  SuccessfulRescale  horizontal-pod-autoscaler  New size: 2; reason: All metrics below target
Normal  SuccessfulRescale  horizontal-pod-autoscaler  New size: 1; reason: All metrics below target
```

So 3 → 2 → 1, **one pod per minute**, after the 120s stabilization
window. Both are set in the HPA's `behavior.scaleDown` block. To keep 3
replicas, raise the HPA's floor instead of fighting it:

```bash
kubectl patch hpa hospital-service -n sentinelcloud -p '{"spec":{"minReplicas":3}}'
```

(PowerShell quoting of inline JSON differs between versions. There,
run `kubectl edit hpa hospital-service -n sentinelcloud` and change
`minReplicas` in the editor instead.)

…or, to demonstrate pure manual scaling, remove the autoscaler first:
`kubectl delete hpa hospital-service -n sentinelcloud` (`kubectl apply
-k k8s/` recreates it).

### 7.5 Scaling down

```bash
kubectl scale deployment hospital-service --replicas=1 -n sentinelcloud
```

For each pod being removed:
1. It's marked `Terminating` and removed from the Service's endpoints
   (no new requests).
2. In parallel, `preStop: sleep 5` runs. That gives kube-proxy on every
   node time to apply the endpoint removal.
3. Then SIGTERM. The Node process stops accepting connections, finishes
   in-flight requests, closes its DB pool and exits 0. Its RabbitMQ
   connection closes, so any unacked messages return to the queue for
   the surviving replica.

Measured: about 6s from `kubectl delete pod` to fully gone, with no
dropped requests.

### 7.6 Autoscaling under load (HPA demo, ambulance-service)

`docs/ARCHITECTURE.md` §8 names the Ambulance Service as the autoscaling
showcase: it's the service that would take the load during a simulated
mass-casualty event. Every Deployment has an HPA, though, so the same
commands work for any of them.

```bash
kubectl get hpa ambulance-service -n sentinelcloud          # e.g. cpu: 2%/70%, REPLICAS 1

kubectl run loadgen -n sentinelcloud --image=busybox:1.36 --restart=Never -- /bin/sh -c "for i in 1 2 3 4 5 6; do (while true; do wget -q -O /dev/null http://ambulance-service:8083/health/ready; done) & done; wait"

kubectl get hpa ambulance-service -n sentinelcloud -w        # second terminal: kubectl get pods -n sentinelcloud -l app.kubernetes.io/name=ambulance-service -w
```

Each request to `/health/ready` runs a `SELECT 1` against Postgres, so
6 tight loops push CPU above the 70% target (70% of the 100m
**request** = 70m average). The HPA then adds pods, at most 2 every 30s
(`behavior.scaleUp`), up to `maxReplicas: 5`. If utilization stays
under target on a fast machine, raise the loop count. Stop the load and
watch it scale back down, one pod per minute after 2 quiet minutes
(`behavior.scaleDown`):

```bash
kubectl delete pod loadgen -n sentinelcloud
kubectl describe hpa ambulance-service -n sentinelcloud      # Events: "New size: N; reason: …"
```

Recorded on the test cluster with a CPU-heavy test endpoint:
ambulance-service scaled 1 → 2 → 3 → 4 → 5 in ~45s (`cpu: 221%/70%`
at peak). After the load stopped it went 5 → 4 → 3 → 2, with the first
removal ~2½ minutes later and then one per minute.

## 9. Resource requests and limits

| Workload | CPU request | Mem request | CPU limit | Mem limit | Reasoning |
|---|---|---|---|---|---|
| Node services (gateway, hospital, ambulance, disaster, notification) | 100m | 128Mi | 500m | 256Mi | Express apps idle at a few millicores and well under 128Mi; 100m makes the HPA's 70% target = 70m |
| auth-service | 100m | 128Mi | **1** | 256Mi | bcrypt (12 rounds) is deliberately CPU-heavy; a low CPU limit would make every login slow |
| Spring Boot (blood-bank, power) | 250m | 512Mi | 1500m | 768Mi | JVM + Hibernate + Flyway; the high CPU limit speeds up boot. Heap = 65% of 768Mi via `MaxRAMPercentage` |
| frontend (nginx) | 25m | 32Mi | 200m | 64Mi | serves static files |
| postgres | 100m | 256Mi | 1 | 512Mi | 6 small databases |
| rabbitmq | 200m | 384Mi | 1 | 768Mi | `vm_memory_high_watermark.absolute = 400MiB` keeps Erlang inside the limit |
| redis | 50m | 64Mi | 250m | 192Mi | `--maxmemory 100mb` so Redis evicts before the kubelet OOM-kills it |
| init containers | 10m | 16Mi | 100m | 32Mi | just `nc` in a loop |

**Total at 1 replica each: 1.475 CPU and 2,528 Mi requested.**

- **Requests** are what the scheduler reserves on a node. A pod only
  lands where its requests fit, which is why an undersized Minikube
  shows `Pending`. They're also the denominator of HPA utilization.
- **Limits** are hard ceilings. CPU above the limit is **throttled** (the
  pod slows down). Memory above the limit is **OOM-killed** (the pod
  restarts, with `OOMKilled` in `kubectl describe`). Memory requests
  are set close to real usage because memory can't be throttled, only
  killed.
- All app pods are QoS class **Burstable** (requests < limits). They're
  guaranteed their requests and may burst toward their limits when the
  node has spare capacity.

## 10. Probes

| Probe | Node services | Spring services | Infra |
|---|---|---|---|
| **startup** | `/health` every 5s, ≤ 150s | `/health/liveness` every 5s, ≤ 5 min | `pg_isready` (TCP) ≤ 3 min · `rabbitmq-diagnostics ping` ≤ 5 min |
| **liveness** | `/health`, no dependency checks | `/health/liveness` | `pg_isready` · `redis-cli ping` · `rabbitmq-diagnostics ping` |
| **readiness** | `/health/ready`: Postgres (+ RabbitMQ for disaster, Redis + RabbitMQ for notification; gateway: none since Phase 10) | `/health/readiness` = readiness state + DB | `pg_isready` · `redis-cli ping` · `check_port_connectivity` |

The design rules behind those choices:
- **Liveness never checks dependencies.** If Postgres goes down, a
  liveness probe that checked the DB would restart **every** service pod
  in a loop, even though restarting them fixes nothing. Instead
  **readiness** fails, pods leave the Service endpoints (no traffic,
  clean 503s at the gateway), and they rejoin automatically once
  Postgres is back.
- **Startup probes protect slow boots.** Without one, a liveness probe
  tuned for steady state would kill a JVM that is still running Flyway.
  Liveness and readiness only begin after the startup probe succeeds.
- **`pg_isready -h 127.0.0.1` (TCP), not the socket.** During first-time
  init the Postgres image runs a temporary socket-only server. A socket
  check would mark it Ready, and services would connect to a server
  that's about to restart.
- **The frontend probes nginx's own `/healthz`**, not the gateway, so a
  backend outage can't get the static frontend restarted.

## 11. ConfigMaps and Secrets

- `sentinelcloud-common`: hostnames and ports shared by everyone. Each
  `*_HOST` value is just a Service name.
- `<service>-config` (one per app): `PORT`, `DB_NAME`, the gateway's
  downstream URLs, auth's token lifetimes, and so on.
- `sentinelcloud-secrets-<hash>`: generated by the local overlay from
  `k8s/overlays/local/secrets.env`. That file is **gitignored**; you
  create it from `secrets.env.example`, so real values are never
  committed (`docs/ARCHITECTURE.md` §10). Pods receive values via `secretKeyRef`.
  Composite values are built **in the manifest** with Kubernetes'
  `$(VAR)` expansion, so the password lives in only one place:

  ```yaml
  - name: RABBITMQ_URL
    value: "amqp://$(RABBITMQ_USER):$(RABBITMQ_PASSWORD)@$(RABBITMQ_HOST):$(RABBITMQ_PORT)"
  ```

  On the test cluster this expanded to
  `amqp://sentinel:sentinel_dev_password@rabbitmq:5672` inside the pod.
- **Changing a secret:** edit `k8s/overlays/local/secrets.env` and run
  `kubectl apply -k k8s/overlays/local`. The content hash in the Secret's name changes,
  Kustomize updates every reference, and every affected Deployment does
  a rolling restart on its own. Plain ConfigMaps don't roll pods. After
  editing one, run `kubectl rollout restart deployment -n sentinelcloud`.
- **Real environments:** create the Secret out-of-band in that
  environment's overlay instead of generating it (or use Sealed Secrets /
  External Secrets). The base manifests don't change:

  ```bash
  kubectl create secret generic sentinelcloud-secrets -n sentinelcloud --from-env-file=path/to/real-secrets.env
  ```
- `enableServiceLinks: false` on every pod. Kubernetes otherwise injects
  Docker-link-style variables such as `GATEWAY_PORT=tcp://10.43.73.188:8080`
  into every pod (seen on the test cluster). A ClusterIP Service named
  `redis` would inject `REDIS_PORT=tcp://…`, colliding with the real
  `REDIS_PORT` setting.

## 12. Persistent volumes

Postgres, RabbitMQ and Redis are **StatefulSets** with
`volumeClaimTemplates`. Each pod gets its own PVC (`data-postgres-0`, …).
The cluster's default StorageClass (`standard` on Kind and Minikube)
**dynamically provisions** a PersistentVolume for each claim, so no
hand-written PV manifests are needed. `kubectl get pv` lists what was
created.

Verified on the test cluster: wrote a marker file into Postgres's volume,
deleted `postgres-0`, and the StatefulSet recreated it (new pod UID)
bound to the **same** PVC with the marker intact.

The 9 application Deployments are **stateless**. All their state is in
Postgres, RabbitMQ or Redis, which is exactly what lets them scale
horizontally.

## 13. Deleting the deployment

```bash
# Everything, INCLUDING data (the namespace and its PVCs go, the PVs are reclaimed):
kubectl delete -k k8s/overlays/local

# Workloads only, KEEPING the data volumes (the next `kubectl apply -k k8s/overlays/local` reattaches them):
kubectl delete deployments,statefulsets,services,hpa,configmaps,secrets --all -n sentinelcloud

# Delete the whole cluster:
kind delete cluster --name sentinelcloud
minikube delete                  # or `minikube stop` to pause it and keep everything
```

`kubectl delete -k k8s/overlays/local` took ~20s on the test cluster.

## 15. Likely errors and fixes

| Symptom | Cause | Fix |
|---|---|---|
| `ErrImagePull` / `ImagePullBackOff` on a `sentinelcloud/*` image | image not built, or not loaded into the cluster, or a tag mismatch | Kind: rerun `kind load docker-image …`. Minikube: `minikube image ls`. Tags must be `:1.0.0` |
| `ImagePullBackOff` on postgres/redis/rabbitmq | no internet, or Docker Hub rate limit | `docker pull postgres:16-alpine` on the host, then `kind load docker-image postgres:16-alpine --name sentinelcloud` (same for the other two) |
| Pods `Pending`, event `Insufficient cpu` / `memory` | cluster smaller than the requests in §9 | Minikube: `minikube delete && minikube start --cpus=4 --memory=6g`. Docker Desktop: raise CPUs/RAM in Settings → Resources |
| `Init:0/1` for a long time | Postgres not Ready yet (first start runs initdb + pulls the image) | `kubectl logs -n sentinelcloud statefulset/postgres`. It normally clears within 1–3 minutes |
| `kubectl apply -k` fails: `secrets.env: no such file or directory` | the gitignored Secret file wasn't created | `./scripts/generate-secrets.sh k8s` |
| `CreateContainerConfigError` mentioning a secret key | `secrets.env` edited and a key removed or renamed | restore the key names from `secrets.env.example` |
| HPA shows `<unknown>/70%` | metrics-server missing or not ready | §4.2 (Kind) or `minikube addons enable metrics-server`, then wait ~1 minute |
| blood-bank/power `CrashLoopBackOff`, `OOMKilled` in describe | heap + metaspace exceeded 768Mi | raise the memory limit in `k8s/base/apps/<svc>.yaml` (e.g. 1Gi) and re-apply |
| blood-bank/power restarted during boot, `Startup probe failed` | very slow machine (> 5 minutes to boot) | raise `startupProbe.failureThreshold` |
| frontend `CrashLoopBackOff`, log says `host not found in upstream "gateway:8080"` | nginx started before the gateway Service existed (only if applied piecemeal) | it self-heals on restart; `kubectl apply -k k8s/overlays/local` creates all Services together |
| frontend crash, `Read-only file system` in log | an nginx image variant writing outside `/tmp` / `conf.d` | remove `readOnlyRootFilesystem: true` from `k8s/base/apps/frontend.yaml` |
| `localhost:30080` not reachable | Minikube, or a Kind cluster created without `k8s/cluster/kind-cluster.yaml` | `kubectl port-forward -n sentinelcloud svc/frontend 8080:80` |
| Live dashboard shows "closed" briefly after scaling notification-service down | its WebSocket was on the removed pod | expected: the client reconnects within ~1s and lands on a surviving replica |
| Old data/admin password still there after editing secrets | Postgres only reads `POSTGRES_*` and the init script when its volume is **empty** | `kubectl delete -k k8s/overlays/local` (wipes PVCs), then apply again |

## 16. Deviations from the plan in `docs/ARCHITECTURE.md` §8

| Plan | As built | Why |
|---|---|---|
| `Ingress` routing `/api/*` to the gateway, self-signed TLS locally | **NodePort** on the frontend Service; nginx in the frontend pod proxies `/api`, `/ws`, `/health` to the gateway | an Ingress needs a controller add-on that's installed differently on Kind and Minikube. NodePort + port-forward work on both with zero add-ons, and still give one entry point and same-origin API calls. Adding an Ingress later is a single new object in an overlay |
| `Deployment` with 2 fixed replicas per service | replica count owned by an **HPA**, `minReplicas: 1` | 9 services × 2 would double the laptop resource budget (§9). Scaling is demonstrated explicitly instead (§7) |
| HPA on the Ambulance Service | HPAs on **all 9** Deployments; ambulance used for the load demo (§7.6) | same cost, more realistic |
| `k8s/base` + `overlays/local` + `overlays/cloud` | `base` + `overlays/local` | no cloud target in scope (no paid services). The base is ready for a cloud overlay |

## 17. Known limitations

- **Single Postgres / RabbitMQ / Redis instance.** Stateful services run
  with 1 replica, which is right for a laptop. HA would mean an operator:
  CloudNativePG, the RabbitMQ Cluster Operator, Redis Sentinel.
- **The login rate limiter is per auth-service replica** (in-memory
  store). With N replicas a client gets up to N × 20 attempts per 15
  minutes. A Redis-backed store (`rate-limit-redis`) would make it
  cluster-wide.
- **No Ingress / TLS.** A NodePort is the simplest free option on both
  local tools. An ingress-nginx controller + cert-manager would be the
  next step.
- **No PodDisruptionBudgets.** With `minReplicas: 1`, a PDB would block
  `kubectl drain` on a single-node cluster. Add them alongside
  `minReplicas ≥ 2` in a multi-node environment.
- ~~Prometheus and Grafana are not part of the Kubernetes deployment.~~
  Added in Phase 10, see [`PHASE-10-MONITORING.md`](PHASE-10-MONITORING.md).
